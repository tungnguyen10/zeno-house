## Confirmed integrity gap and source repair in this stabilization branch

`server/repositories/inventory.ts` previously implemented both `replaceTemplate()` and `replaceRoom()` as separate `DELETE` then `INSERT` requests. If the second request failed, the existing inventory could be permanently erased.

The existing migration `20261112005547_inventory_lite.sql` already defines `replace_inventory_template(uuid,jsonb)` and `replace_room_inventory(uuid,jsonb)` as service-role-only, single-transaction replacements. They validate the full payload before deleting, and serialize competing inventory changes using locks. `app/types/database.types.ts` at the reviewed SHA includes both signatures.

**Change in this PR**: route both repository methods through these typed atomic RPCs, including an empty array (atomic clear), and sort returned rows by `sort_order`. Added repository regression tests for call ownership, ordering, empty clears and failure propagation. No new DB migration is required for these two methods **if** the deployed schema matches the recorded migration.

**Open gap (source repaired and migration applied 2026-11-17)**: `replaceContract()` now calls `replace_contract_inventory` from `20261117090000_contract_inventory_rpcs.sql`. The RPC locks the contract row, rejects issued/signed documents with `CONTRACT_INVENTORY_LOCKED`, validates the payload and replaces in one transaction. The same migration adds `find_handover_inventory`, a bounded recursive lookup that replaces up to 40 sequential queries. The migration was pushed to production and grants were confirmed (service-role only, invoker). Behavioral SQL verification (`supabase/verification/contract_inventory_rpcs.sql`) passed on production 2026-11-17 (rolled back, grants confirmed); the issued-document lock path is still unverified. `app/types/database.types.ts` was regenerated with Supabase CLI 3.1 (adds `tenant_ocr_usage` and both RPCs); jsonb NOT NULL inserts now use `NonNullable<Json>`.

## Migration drift / order

- `20261112005547_inventory_lite.sql` defines stricter `apply_inventory_template`, `create_rooms_batch_idempotent` and `create_contract_with_handover_and_inventory`.
- `20261111110000_inventory_lite.sql` was applied to production later in calendar time, overwriting those signatures with weaker function bodies.
- PR #26 introduced `20261116100000_inventory_lite_functions_hardening.sql` restoring all **three** stricter bodies after both older files in timestamp order.
- New `tests/config/inventory-hardening-order.test.ts` asserts the restored function definitions match the hardened originals and retain service-role/invoker rules. It does not prove that production actually executed the migration.
- **Deployment prerequisite**: read-only inspect `supabase_migrations.schema_migrations`, `pg_get_functiondef`, function signatures and `has_function_privilege` in the authorized target project. If the last migration is missing, follow the normal approved backup/dry-run/push/SQL-verification/type-generation path. Never re-run an older inventory migration to fix function drift.
